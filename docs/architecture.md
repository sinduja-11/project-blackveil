
# PROJECT BLACKVEIL
## System Architecture Document
### Adaptive Deception and Intelligence Defence for Permissioned Blockchains

---

## 1. Introduction

This document describes the system architecture of PROJECT BLACKVEIL, an adaptive security layer designed for permissioned blockchain networks.

PROJECT BLACKVEIL aims to protect permissioned blockchain environments against threats involving stolen credentials, malicious authorised nodes, suspicious reconnaissance and abnormal transaction behaviour.

The system continuously evaluates node behaviour, calculates dynamic risk scores and applies proportionate security responses.

Unlike traditional security mechanisms that primarily focus on detecting and blocking suspicious activity, BLACKVEIL introduces an isolated, state-aware decoy blockchain environment where eligible high-risk sessions can be redirected for investigation.

The real blockchain independently validates every transaction, ensuring that BLACKVEIL operates as an additional security layer rather than a replacement for blockchain security.

## 2. Architectural Overview

The architecture consists of the following major components:

1. Simulated Blockchain Nodes.
2. BLACKVEIL Security Gateway.
3. Behavioural Risk Engine.
4. Adaptive Response Engine.
5. Real Permissioned Blockchain.
6. Transaction Integrity Guardian.
7. Isolated Decoy Blockchain.
8. Forensic Evidence System.
9. Security Dashboard.
10. Threat Intelligence and Policy Management.

The gateway, behavioural risk engine and adaptive response engine form the central request-processing layer.

The risk engine is implemented as an internal module within the gateway process in the initial prototype to avoid unnecessary network communication overhead.

The real and decoy blockchain environments remain logically and network-isolated from each other.

## 3. Component Architecture

### 3.1 Simulated Blockchain Nodes

The prototype shall contain eight simulated nodes with different behavioural profiles.

Each node shall have:

- A unique node identifier.
- An associated Ed25519 key pair.
- An assigned operational role.
- A behavioural baseline.
- A history of requests and transactions.

Different profiles shall represent legitimate network activities, such as:

- High-volume payment processing.
- Read-heavy auditing.
- Batch settlement.
- General transaction processing.
- Administrative operations.

The purpose of using different profiles is to establish that legitimate nodes may naturally exhibit different behavioural patterns.

BLACKVEIL shall evaluate each node against its expected role and historical behaviour rather than assuming that every node should behave identically.

### 3.2 BLACKVEIL Security Gateway

The security gateway acts as the central entry point for requests generated by participating nodes.

All simulated node communication with the blockchain environments shall pass through this gateway.

Responsibilities include:

- Receiving incoming node requests.
- Verifying cryptographic identity.
- Validating request structure.
- Maintaining session information.
- Extracting behavioural information.
- Invoking the integrated behavioural risk engine.
- Applying adaptive security decisions.
- Routing eligible requests to the appropriate environment.
- Recording security events.

The gateway shall not automatically grant unrestricted access simply because a node has successfully authenticated.

Identity verification establishes that the credentials are valid, while behavioural assessment determines the appropriate level of access.

The gateway shall maintain a record of the information returned to each session so that the decoy environment can preserve session continuity when diversion occurs.

### 3.2.1 Request Inspection and Data Exposure Control

All incoming requests shall be inspected by the gateway before they are forwarded to any blockchain environment.

The system shall implement progressive exposure controls.

The following rules shall apply:

1. Low-risk sessions shall receive only role-authorised access.
2. High-value channels and sensitive operations shall require stricter access conditions, even when the risk score is low.
3. Suspicious requests shall be restricted or denied before additional information is disclosed.
4. The gateway shall maintain a record of information successfully returned to each session.
5. Once a session is diverted, further access to the real blockchain shall be denied.
6. Direct node access to the real blockchain shall not be permitted.

Information disclosed before diversion cannot be retroactively withdrawn.

Therefore, the system shall minimise unnecessary information exposure through role-based access controls, channel sensitivity policies and progressive restrictions.

### 3.3 Behavioural Risk Engine

The behavioural risk engine evaluates node behaviour using a 60-second sliding window.

It operates as an internal module within the BLACKVEIL gateway process in the initial prototype.

The engine extracts seven behavioural features:

1. Request rate deviation.
2. Operation-sequence surprise.
3. Distinct channels and keys accessed.
4. Transaction value deviation.
5. Read-to-write ratio shift.
6. Source changes, including IP address, TLS fingerprint and time of day.
7. Integrity violations, including replayed nonces, invalid signatures and rejected transactions.

The engine combines three detection mechanisms.

#### A. Rule-Based Detection

Rule-based detection identifies predefined suspicious conditions.

Examples include:

- Repeated invalid signatures.
- Replayed nonces.
- Unusual access attempts.
- Suspicious operation sequences.

Hard-rule events may immediately establish a high minimum risk score.

#### B. Isolation Forest

Isolation Forest identifies behavioural patterns that differ significantly from normal node activity.

The model shall be trained using benign simulator traffic representing different legitimate node profiles.

Scripted attack traces shall be kept separate from the benign training dataset.

#### C. CUSUM-Based Behavioural Drift Detection

CUSUM identifies gradual behavioural changes that may not produce an immediate anomaly.

It is particularly useful for detecting slow-and-low attacks where suspicious actions are distributed over an extended period.

#### Risk Calculation

The system shall calculate a risk score between 0 and 100.

The smoothed risk score shall be calculated using:

R_t = αR_(t-1) + (1-α) max(S_rules, 0.6S_model + 0.4S_drift)

Where:

- R_t represents the current smoothed risk score.
- R_(t-1) represents the previous risk score.
- α is the smoothing factor, set to 0.7.
- S_rules represents rule-based risk.
- S_model represents anomaly detection risk.
- S_drift represents behavioural drift risk.

All component scores shall be scaled between 0 and 100.

The engine shall also record the three strongest contributing behavioural features to provide explainability for security decisions.

#### Cold-Start Handling

New nodes may not have enough historical activity to establish individual behavioural baselines.

During this period:

- Pooled peer-group baselines shall be used.
- Stricter access thresholds shall apply.
- Node-specific baselines shall become active after at least 200 observed requests.

### 3.4 Adaptive Response Engine

The adaptive response engine maps risk scores to proportionate security responses.

The system shall support four response levels.

| Risk Score | Response | Behaviour |
|---|---|---|
| 0–29 | Observe | Normal service with full security logging |
| 30–54 | Challenge | Fresh signed challenge-response and tighter rate limits |
| 55–74 | Restrict | Read-only operation, transaction value caps and additional endorsement requirements |
| 75–100 | Divert | Redirect eligible high-risk sessions to the isolated decoy environment |

#### Observe

Normal operations are permitted according to the node's role and channel permissions.

All relevant activities continue to be recorded.

#### Challenge

The gateway requests fresh signed challenge-response verification.

Additional rate limits are applied.

Successful verification may allow the session to remain at this level or return to a lower level after reassessment.

#### Restrict

The gateway limits the operations available to the suspicious session.

Restrictions may include:

- Read-only access.
- Transaction value caps.
- Additional endorsing-node requirements for writes.

#### Divert

Eligible high-risk sessions are silently redirected to the isolated decoy blockchain.

The diverted session shall not receive further access to the real blockchain.

#### Anti-Flapping Mechanism

The response engine shall prevent rapid switching between security levels.

The following rules shall apply:

1. Response severity shall increase quickly when risk rises.
2. A session shall move to a lower response level only after three consecutive windows with scores at least five points below the current band's lower boundary.
3. Diversion shall require two consecutive risk windows at or above 75, or a qualifying hard-rule event such as a replayed nonce combined with invalid signatures.
4. Session history shall be maintained for investigation and recovery.

#### Consensus-Critical Node Protection

Nodes carrying critical consensus responsibilities, such as a sole orderer, shall never be automatically diverted.

If such a node exhibits suspicious behaviour:

- BLACKVEIL shall apply appropriate restrictions.
- The incident shall be escalated to a human analyst.
- Critical operations shall remain subject to independent blockchain validation and consensus policies.

This introduces a known residual risk.

An attacker using compromised consensus-critical credentials may affect availability or consensus-related operations before human intervention.

The prototype shall document and evaluate this limitation rather than claiming complete protection against consensus-level compromise.

#### Recovery After Diversion

Recovery from diversion shall require:

- Analyst review.
- Key rotation.
- Review of the session history journal.
- Resubmission of legitimate transactions through normal blockchain validation.

Decoy transactions shall never be automatically replayed into the real blockchain.

### 3.5 Real Permissioned Blockchain

The real blockchain represents the protected ledger environment.

It shall handle legitimate blockchain operations and maintain the actual ledger state.

The real blockchain shall remain independently responsible for:

- Transaction validation.
- Signature verification.
- Permission enforcement.
- Nonce and sequence validation.
- Endorsement policy enforcement.
- Business invariant validation.

Every transaction shall be independently validated before commitment.

The real blockchain shall not depend entirely on the gateway's risk assessment for transaction integrity.

Even if the gateway incorrectly permits a request, the real blockchain shall independently enforce its transaction validation rules.

### 3.6 Transaction Integrity Guardian

The transaction integrity guardian is responsible for enforcing transaction-level security rules in the real blockchain's commit path.

It shall validate:

1. Ed25519 signature and enrolled sender identity.
2. Nonce and sequence correctness.
3. Channel and operation permissions.
4. Business invariants, such as non-negative balances and asset conservation.
5. Endorsement requirements.
6. Applicable transaction value limits.

The guardian shall fail closed.

Transactions that cannot be successfully validated shall not be committed.

### 3.6.1 Consensus-Critical Node Protection

Nodes carrying critical consensus responsibilities shall not be automatically diverted.

If suspicious behaviour is detected from such a node, BLACKVEIL shall apply restrictions and escalate the incident to a human analyst.

This limitation introduces a residual risk of consensus-related disruption before human intervention.

The prototype shall explicitly include this limitation in its threat model and evaluation.

### 3.7 Isolated Decoy Blockchain

The decoy blockchain is a separate permissioned blockchain environment used to investigate suspicious sessions.

It shall provide a realistic environment that resembles the structure and behaviour of the real blockchain without exposing real blockchain infrastructure.

Its design includes:

- Synthetic accounts and balances.
- Synthetic transactions.
- Matching channel names and contract interfaces.
- Similar block and transaction formats.
- Similar error-message structures.
- An independent hash-chained ledger.
- Per-session copy-on-write data overlays.
- Independent cryptographic keys.

#### Session Continuity

The decoy shall preserve the exact response values previously served to a session, wherever those values are permitted for continuity seeding.

For example, if a session previously received a synthetic account balance, the same balance shall be represented in its decoy overlay after diversion.

The following rules shall apply:

1. Only information actually disclosed to that session may be seeded.
2. The system shall not copy the entire real ledger.
3. Sensitive real information shall be masked or replaced before it is served by the gateway.
4. The exact permitted response representation shall be maintained within the session's isolated overlay.
5. Subsequent decoy writes shall update that session's overlay and be reflected in later reads.
6. Separate sessions shall not share mutable overlay state.

This approach preserves continuity while preventing unrestricted copying of real blockchain information.

#### Decoy State Synchronisation

The decoy shall maintain state changes within each session's isolated overlay.

The environment shall advance at a similar block cadence to the real blockchain, with small controlled timing variations.

The objective is to prevent obvious differences in behaviour that could reveal the decoy environment through simple fingerprinting.

#### Isolation Requirements

The decoy environment shall satisfy the following isolation requirements:

1. Separate container network.
2. No network route to the real blockchain or its database.
3. Blocked outbound network access.
4. Independent decoy cryptographic keys.
5. No publicly accessible decoy address.
6. Gateway-only access.
7. CPU, memory and storage quotas.
8. Canary credentials for identifying suspicious credential reuse.

#### Fidelity Evaluation

The decoy shall be evaluated using scripted fingerprinting probes.

The evaluation shall examine:

- Block-time regularity.
- Hash linkage.
- Latency distribution.
- Balance patterns.
- Error-message wording.

The system shall report the proportion of probes that distinguish the decoy from the real environment.

The target is for no more than 10% of the defined fingerprinting probes to distinguish the two environments.

The target shall be treated as an evaluation objective rather than an assumed result.

### 3.8 Forensic Evidence System

The forensic evidence system records security events generated by:

- Security gateway.
- Behavioural risk engine.
- Adaptive response engine.
- Real blockchain transaction guardian.
- Decoy blockchain environment.

Each event shall be stored as canonical JSON.

Events shall be linked using SHA-256:

h_i = SHA256(h_(i-1) || event_i)

Where:

- h_i represents the current event hash.
- h_(i-1) represents the previous event hash.
- event_i represents the current canonical event data.

The gateway shall digitally sign forensic event batches using its Ed25519 key.

The latest forensic chain head shall periodically be anchored to the real blockchain.

A verification mechanism shall recompute the hash chain and identify the first broken link.

Database access controls shall prevent unauthorised modification of recorded events.

The forensic system shall support incident reconstruction through a chronological event history.

### 3.9 Security Dashboard

The dashboard provides a visual interface for security monitoring and investigation.

It shall display:

- Registered nodes.
- Node activity.
- Current risk scores.
- Risk score history.
- Behavioural feature contributions.
- Adaptive response decisions.
- Suspicious session information.
- Decoy interactions.
- Forensic incident timelines.
- Evidence integrity verification results.
- Node restriction and diversion status.

The dashboard shall make security information understandable to an analyst without requiring manual examination of raw event records.

### 3.10 Threat Intelligence and Policy Management

Confirmed incidents shall generate candidate behavioural indicators.

Potential improvements may include:

- New behavioural rules.
- Adjusted risk thresholds.
- Modified feature weights.
- Additional suspicious operation patterns.

Before deployment, candidate policies shall be tested against benign and attack traces.

A candidate policy shall be eligible for approval only if it improves detection without increasing the false-positive rate by more than one percentage point in the defined shadow evaluation.

Live policy updates shall require human approval.

Approved policy bundles shall be:

- Digitally signed.
- Version controlled.
- Recorded in the forensic evidence chain.
- Reversible through a rollback mechanism.

Decoy activity shall never directly modify live security policies.

Only confirmed malicious sessions, supported by hard-rule evidence or analyst decisions, shall contribute to candidate generation.

Anti-poisoning measures shall include:

- Limiting the influence of individual sessions.
- Rate-limiting policy changes.
- Training models only on benign-labelled traffic with outliers trimmed.
- Requiring human approval before live deployment.

## 4. Request Processing Workflow

The request processing workflow describes how BLACKVEIL handles requests from participating nodes.

1. A simulated node sends a request to the BLACKVEIL gateway.
2. The gateway verifies the node's cryptographic identity.
3. The gateway validates the request structure and checks role-based permissions.
4. Behavioural information is extracted.
5. The integrated risk engine updates the node's behavioural features and calculates the risk score.
6. The adaptive response engine determines the appropriate security response.
7. The gateway permits, challenges, restricts, rejects or diverts the request according to the applicable policy.
8. Eligible high-risk sessions are redirected to the isolated decoy blockchain.
9. Permitted real blockchain transactions undergo independent validation by the transaction integrity guardian.
10. Security events are recorded in the forensic evidence system.
11. The dashboard presents the resulting security information.
12. Confirmed incidents may generate candidate security policy improvements through human-reviewed processes.

All request decisions shall be recorded with sufficient information to explain why a particular response was selected.

## 5. Data Flow and Isolation

The architecture maintains two separate blockchain environments.

### 5.1 Real Environment

The real environment:

- Contains the protected ledger.
- Processes legitimate blockchain operations.
- Uses independent transaction validation.
- Maintains real-environment cryptographic keys.
- Enforces role and channel permissions.
- Does not permit direct access from simulated nodes.

All node requests shall pass through the BLACKVEIL gateway.

### 5.2 Decoy Environment

The decoy environment:

- Contains synthetic blockchain data.
- Receives eligible diverted sessions through the gateway.
- Maintains isolated session-specific state.
- Uses independent cryptographic keys.
- Maintains its own ledger.
- Has no network route to real blockchain infrastructure.

No decoy transaction shall be automatically replayed into the real blockchain.

If an incident is cleared, the analyst must review the session history, ensure key rotation and have the legitimate owner resubmit required transactions through normal validation.

### 5.3 Information Exposure Boundary

Information disclosed before diversion cannot be retroactively recovered.

Therefore:

- The gateway shall minimise unnecessary information exposure.
- Sensitive channels shall have stricter access policies.
- Suspicious requests shall be restricted before additional disclosure.
- Only previously served permitted response values shall be used for decoy continuity.
- The entire real ledger shall never be copied into the decoy.

## 6. Deployment Architecture

The initial prototype shall run on a single development machine using Docker Compose.

The deployment shall separate the following logical services:

1. Simulated node service.
2. BLACKVEIL gateway, including its integrated behavioural risk engine and adaptive response logic.
3. Real blockchain simulator.
4. Decoy blockchain service.
5. PostgreSQL database.
6. Forensic verification service.
7. Dashboard frontend.
8. Threat intelligence and policy management module.

The gateway and risk engine shall run within the same application process in the initial prototype to avoid an additional network hop for each request.

The system shall maintain modular internal interfaces so that these responsibilities can be separated into independent services in a future deployment if necessary.

Container network policies shall separate the real and decoy environments.

The gateway shall be the only permitted communication path into the decoy environment.

Simulated nodes shall not have direct network access to the real blockchain or its database.

The deployment shall use resource limits to prevent the decoy environment from consuming excessive resources.

## 7. Architecture Design Principles

PROJECT BLACKVEIL follows the following design principles.

### 7.1 Zero-Trust Behavioural Assessment

Authentication alone shall not establish ongoing trust.

Node behaviour shall be continuously evaluated.

### 7.2 Adaptive Security

Security responses shall change according to the severity of observed behaviour.

### 7.3 Deception-Based Investigation

Eligible suspicious sessions shall be redirected to an isolated decoy environment for investigation.

### 7.4 Independent Ledger Protection

The real blockchain shall independently validate every transaction before commitment.

### 7.5 Strong Isolation

The decoy shall not have access to real blockchain data, databases or cryptographic keys.

### 7.6 Tamper-Evident Evidence

Security events shall be cryptographically linked and verifiable.

### 7.7 Human-Supervised Intelligence

Confirmed incidents may improve security policies through controlled testing, approval and rollback.

### 7.8 Modular Implementation

Components shall remain logically independent and testable, even when multiple components operate within the same application process.

### 7.9 Fail-Safe Operation

A failure in a BLACKVEIL component shall not create an automatic route around the real blockchain's security controls.

## 8. Failure Handling and Safe Degradation

The system shall implement fail-safe behaviour to prevent component failures from bypassing security controls.

### 8.1 Gateway Failure

If the gateway becomes unavailable:

- Simulated nodes shall not receive direct access to the real blockchain.
- Incoming requests shall be rejected.
- No alternate route shall bypass gateway enforcement.
- The failure shall be recorded when the service is restored.

The gateway shall be treated as a critical security component and a potential single point of failure in the prototype.

### 8.2 Risk Engine Failure

If the behavioural risk engine becomes unavailable or produces an invalid result:

- Protected writes shall fail closed.
- The system shall not grant unrestricted access because risk assessment is unavailable.
- The failure shall generate an operational security event.
- Normal processing shall resume only after risk assessment is restored and validated.

### 8.3 Decoy Failure

If the decoy environment becomes unavailable:

- A diverted session shall remain restricted or quarantined.
- It shall not automatically return to the real blockchain.
- The failure shall be recorded and escalated.
- Recovery shall require health checks and appropriate review.

### 8.4 Forensic Storage Failure

If forensic storage becomes unavailable:

- Security events shall not be silently discarded.
- Protected operations shall be restricted if reliable evidence recording is unavailable.
- Events may be buffered only through a defined, bounded and protected mechanism.
- Normal processing shall resume after evidence storage and integrity checks are restored.

### 8.5 Dashboard Failure

If the dashboard becomes unavailable:

- Security enforcement shall continue independently.
- Gateway decisions shall not depend on dashboard availability.
- Forensic event collection shall continue independently.
- Investigation information shall remain available through the backend once the dashboard is restored.

### 8.6 Recovery Procedures

Recovery shall require:

1. Health checks for the affected component.
2. Verification that required security policies are loaded.
3. Reconciliation of pending security events.
4. Integrity checks on forensic records.
5. Review of previously restricted or diverted sessions.

Sessions shall not automatically regain unrestricted access after component recovery.

Any release shall follow the appropriate security review and recovery procedure.

## 9. Residual Risks and Limitations

The initial prototype has the following known limitations.

### 9.1 Consensus-Critical Node Risk

Consensus-critical nodes cannot be automatically diverted.

An attacker using compromised consensus-critical credentials may affect availability or consensus-related operations before human intervention.

This risk shall be mitigated through restrictions, independent validation and analyst escalation, but is not eliminated.

### 9.2 Pre-Diversion Information Exposure

Information disclosed before diversion cannot be retroactively recovered.

Progressive access controls and sensitive-channel restrictions shall minimise this exposure.

### 9.3 Decoy Fingerprinting

A sufficiently sophisticated attacker may identify differences between the real and decoy environments.

Fingerprinting evaluation shall measure this risk.

Even if the decoy is identified, its isolation must prevent access to real blockchain infrastructure.

### 9.4 Gateway Availability

The single-gateway prototype introduces a potential availability bottleneck and single point of failure.

A production implementation may require redundant gateways and high-availability deployment.

### 9.5 Model Limitations

A sophisticated attacker who closely imitates a legitimate node's historical behaviour may evade behavioural anomaly detection.

The independent transaction integrity guardian remains an additional protection mechanism.

### 9.6 Prototype Scale

The initial implementation shall use eight simulated nodes on a single development machine.

Performance at hundreds or thousands of nodes is not established by this prototype.

### 9.7 Failure Recovery

Fail-safe restrictions may reduce availability during component failures.

The system prioritises protection of the real blockchain over uninterrupted access when critical security components are unavailable.

## 10. Conclusion

The architecture of PROJECT BLACKVEIL combines cryptographic identity verification, behavioural risk assessment, adaptive response, deception technology, independent transaction integrity protection and tamper-evident forensic evidence.

The gateway acts as the central security decision point, while the real and decoy blockchain environments serve separate purposes.

The real blockchain remains protected through independent transaction validation, while suspicious sessions can be investigated within an isolated decoy environment.

The architecture aims to detect suspicious behaviour, limit information exposure, safely investigate potential attacks and maintain the integrity of the protected ledger.

PROJECT BLACKVEIL follows the principle:

"Trust identity, continuously evaluate behaviour, adapt the response, and protect the real ledger."

It doesn't just defend the blockchain. It turns deception into intelligence, and intelligence into defence.
